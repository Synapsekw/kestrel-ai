## Rulings (taken while planning; reviewers should not flag them)

1. **Existing operations that only gain fields keep conforming on `main`.** The alternative, a `BACKEND_PENDING` allowance per operation (what Foundation's C0 did, decision 4), would have masked conformance on `listCloudMeasurements`, `updateCloudMeasurement` and `createCloudMeasurement` for the whole wave. Foundation needed that because the fields came from units that owned their columns. Here C0 owns the columns (`0013`), so it extends the ORM model and the pydantic `CloudMeasurementOut`/`CloudMeasurementResults`/`CloudMeasurementPoint` so the backend really sends every new response field: `status` from the column, `params`/`error`/`job_id`/`finding_id` from the columns, `view` = `null` until B4, and the 17 new results = `null` until B1/B2 compute them. `deletePointCloud`'s new query parameter is ignored by FastAPI until B3, so it conforms unchanged. `updateCloudMeasurement`'s new `finding_id` is accepted and ignored until B1, so it conforms too.
2. **`createCloudMeasurement` is the one `BACKEND_PENDING` entry**, value `"C-B1 and C-B2"`. Its *request* widens (kinds `area`/`profile`, up to 200 points, `params`, `finding_id`, a 202 for profiles), and the backend cannot build those until B1 (area, rings, params, finding) and B2 (profile job) land. Widening the pydantic `Literal` in C0 would turn `area` into a 500 (`LABELS[kind]` KeyError in `measurements.py`). So C0 splits the kind type: `CloudMeasurementKind` (all six, for responses) and `CreatableCloudMeasurementKind` (the four built today, for `CloudMeasurementCreate`). A generated `area` body then answers 422 `validation_error`, which the pending branch accepts (< 500). **Whichever of B1 and B2 merges second deletes the entry.**
3. **All new `CloudMeasurementOut` fields are `required`, nullable where empty.** The spec writes `error?`, `job_id?`, `finding_id?`, but the backend always sends them, and required fields give M1/P1 non-optional types (Foundation C0's convention). The 17 new `CloudMeasurementResults` quantities are required and nullable, like the 15 existing ones.
4. **`CloudMeasurementPoint.group` and the `CloudMeasurementParams` keys are nullable** (`type: [..., "null"]`). Pydantic serialises an unset optional as `null`, and stored rows have no `group` key. A non-nullable optional would fail response validation on every existing measurement.
5. **Names the spec leaves open, fixed here:** `CloudMeasurementStatus` (the status enum as a schema); `CloudMeasurementWithJob {measurement, job}`; `CloudCameraOffsetPut {height_offset_m}`; `CloudCameraSet.fov_assumed: boolean[]` (per camera, the spec's `fov_assumed: true`); `CloudCameraSet.z_p1`/`z_p99` (the echoed `z_stats.p1`/`p99`); `CloudCameraSource.label` is a string, never null (B3 falls back to the set's site, then its folder name); `CloudViewUpload {image, meta}` (the multipart body); `CloudViewSubjectKind`; `CloudClipBox {centre, size, yaw_deg, mode: show_inside | highlight_inside}`; `CloudViewRender.colour_mode` is `rgb | elevation | intensity | classification` (extending `viewer/materialOptions.ts::ColourMode = "rgb" | "elevation"` on `main`, so C-V1's `ColourMode` must use these four strings); `CloudProfile.rgb` is flat `[r, g, b, r, g, b, …]` (3 × `count`).
6. **New error codes:** the spec's `self_intersecting`, `degenerate_polygon`, `ring_needs_three_points`, `collinear_ring`, `profile_out_of_range`, `not_retryable`, `needs_coordinates`, `cloud_has_findings` (details `{count}`), `not_a_cloud_finding`, `bad_view_image` (details `{reason}`) and `no_view`, plus one the spec implies but does not name: **`invalid_finding`** (422 on create and update, for a `finding_id` that is unknown, not a cloud finding, or anchored on another cloud). `getCloudProfile` on a measurement of another kind answers 404 `not_found`: it has no profile. A `failed` or `computing` profile answers 409 `not_ready`.
7. **Stub placement follows the code, not the spec** (§12 says `app/stubs.py`). On `main`, stubs are tuples in `app/pointclouds/router.py::STUBS` mounted by `app/stubs.py::add_stubs`, and `tests/test_pointcloud_stubs.py` already checks them against `EXPECTED_STUBS` and calls each for a 501. C0 fills `STUBS`. The two multipart PUTs need a body-less stub (Review Focus 3), which `router.py` defines locally so F's shared helper stays untouched.
8. **The `view3d` finding paths sit textually in C's block**, directly after `/pointclouds/{cloudId}/exports`, not among F's `/findings` paths. OpenAPI paths are unordered; keeping every C edit contiguous makes the rebase over I-C0 and M-C0 trivial. They are routed through the pointclouds router, whose prefix is `/projects/{projectId}`.
9. **C0 defines every pydantic model the B units will use** (`CloudProfile`, `CloudCamera*`, `CloudView*`, `CloudMeasurementWithJob`), each mirrored against the contract by a test. The four B units then never add schemas to `schemas.py`, only logic, which keeps their parallel rebases conflict-free.
10. **The startup sweep steps are two functions in `app/pointclouds/startup.py`**: `sweep_profiles(handle, runner) -> list[str]` (B2 fills it) and `sweep_views(handle) -> int` (B4 fills it, delegating to its `views.py`). `project_opened` in `app/main.py` calls them as two separate steps, so a failure in one never skips the other.

## Budget

The contract **encodes** C's budget (§13) so the building units cannot drift from it:

- **Background job:** `pointcloud_profile`. A profile create answers 202 `CloudMeasurementWithJob`, and `retryCloudProfile` answers 202 `JobRef`.
