**Goal:** The Catalogue screen's type editor (`TypeEditor`) gains a **Definition** textarea (at most 1000 characters, with a counter) and a **Severity rules** list. Each rule has a condition (`when`, at most 200 characters) and a severity picked from the current scale. Rules can be added (at most 8), reordered with buttons or Alt+↑/Alt+↓, and removed. A rule whose level is no longer on the scale is flagged. Both kinds of type show these fields. Saving goes through the existing `createCatalogueType` and `patchCatalogueType` calls.

**Architecture:**
- Pure rule logic lives in a new `frontend/src/catalogue/severityRulesModel.ts`: `RuleDraft` (a rule with a stable React key), conversion to and from the contract's `SeverityRule`, `moveRule`, `sameRules`, `newRuleLevel` and `validateRules(drafts, scale)`.
- `catalogueModel.ts` extends `TypeDraft` with `definition` and `rules`. `draftOf`, `toCreate`, `toPatch` and `validateTypeDraft` carry the new fields, and a new `supportsDefinition(type)` detects an answer without them.
  - `toCreate` omits an empty definition and an empty rule list.
  - `toPatch` sends `definition` or `severity_rules` (the whole ordered list) only when they changed.
- A new controlled component, `SeverityRulesEditor.tsx`, reads the scale with `useSeverityScale()`. That context is fed app-wide by `CatalogueSeverityProvider` from `useCatalogueSeverity`, so this unit adds no request.
- `TypeEditor.tsx` puts the Definition field inside its **Type** section and a new **Severity rules** section after **Default severity**. It checks the rules against the scale only when the save would send them. It also maps 422 `invalid_severity_rule` to a plain message.
- `api/catalogue.ts` gains the `SeverityRule` type alias and `isInvalidSeverityRule(err)`.

**Tech Stack:** React 18, TypeScript, `openapi-fetch` via `@contract/client`, Tailwind with the Aero glass tokens, vitest + Testing Library (`fakeClient`, `renderWithProviders`), Playwright against the Prism mock with `page.route`.

## Review Focus

These are the five likeliest real breakages, each pinned by a named test:

1. **A type from before `0003`.** After migration it has `definition: null, severity_rules: []`. A rename must PATCH `{ name }` only, show an empty Definition and show the "No rules yet" line. If the answer lacks the fields entirely, the sections are hidden and nothing new is sent.
   - Pinned in Task 2: "copies definition and rules from a type, and reads an answer without them as empty".
   - Pinned in Task 4: "saves a name change on a type from before 0003 without touching definition or rules" and "hides definition and rules for an answer without them and never sends them".
2. **A patch sends only what changed.** Definition only → `{ definition }`. Cleared → `{ definition: null }`. A reorder → the whole list in the new order. Nothing changed → no request (the existing "closes without a request" test).
   - Pinned in Task 2: "patches the definition and the whole rule list only when they changed".
   - Pinned in Task 4: "patches only the definition when only it changed", "clearing the definition sends null" and "sends the whole reordered list when a rule moves".
3. **The scale shrinks to 3 levels while a rule says 4.** The rule is flagged: the select is invalid, shows `Level 4 (removed)` and has a description. A rename still saves. A rules change is blocked, with the rule named, until a level on the scale is chosen.
   - Pinned in Task 3: "a rule whose level left the scale is flagged and keeps its value until changed".
   - Pinned in Task 4: "a rule on a removed level does not block a rename" and "a rules change waits until the removed level is replaced".
4. **Reordering with the keyboard.** Alt+↑/Alt+↓ on any control in a row moves that rule. Focus stays on the same control: React moves DOM nodes on a keyed reorder, and the moved node can lose focus. At the top, **Move up** is disabled and focus falls back to the rule's condition. The position is announced.
   - Pinned in Task 3: "Alt+↓ and Alt+↑ move the focused rule, keep focus on it and announce the position" and "the move buttons keep focus with the moved rule, and fall back to its condition at the top".
5. **Create and server refusal.** A new type without a definition or rules sends the old body, unchanged. With them, it sends them in display order, trimmed. A 422 `invalid_severity_rule` shows a plain message, not the raw server text.
   - Pinned in Task 2: "creates with a definition and rules only when given".
   - Pinned in Task 4: "creates a type with a definition and its rules in the order shown" and "explains a server refusal of the rules"; the existing "creates a defect with a default severity" stays.

## Rulings

1. **The per-rule severity picker is a dense native `Select`**, not `SeverityPicker`. `SeverityPicker` is a 4-per-row tile grid 42 px tall and needs a value that is on the scale. Eight of them would crowd the 340 px inspector, and the grid cannot show a removed level. The `Select` lists the scale as `n Name` and adds `Level k (removed)` only for a stale value. Keyboard, tests and screen readers keep working, as `Select`'s own doc says.
2. **The removed-level check blocks a save only when that save sends the rules.** A rename of a type with a stale rule must still work, because the server only sees `severity_rules` when they are sent. The row is flagged either way.
3. **A new rule starts at the type's default severity** when that level is on the scale; otherwise it starts at the lowest level. An object has no default severity, so its rules start at the lowest level.
4. **The Definition field sits inside the Type section, after Group.** It is not in a section of its own: a section titled "Definition" would give two elements the accessible name "Definition" (the `InspectorSection` region and the textarea).
5. **The live position announcement** is a visually hidden `role="status"` paragraph inside `SeverityRulesEditor`, in the style of R7's section list.
6. **Focus after a change:**
   - A move re-focuses the control that triggered it. If that control is now disabled (**Move up** at the top), focus falls back to the rule's condition input.
   - **Add rule** focuses the new rule's condition.
   - **Remove** focuses the next rule's condition, else the previous one's, else **Add rule**.
7. **Before the catalogue's scale first loads**, DS's default four-level scale is in effect (`CatalogueSeverityProvider`). A rule at level 5–9 can show the stale flag briefly until the real scale arrives. This is accepted; the check is re-run from context on every render.
8. **`TypesPane` has no read-only preview of a type.** The table shows only chip, group, default severity, hotkey and state, and the editor is the only detail view. The definition is therefore not shown anywhere else. The coordinator allowed this: "only if trivial; otherwise leave it out".

## Deviations from the spec

- The spec §9 table names `CatalogueTypeUpdate`. The code and the index use `CatalogueTypePatch`, and this plan follows the code (programme ruling R1).
- The spec §8 "rules list (add, reorder, remove; severity picker per rule)". Reorder is by buttons and Alt+↑/Alt+↓, not by drag: eight short rows do not need drag. The per-rule picker is a `Select` (Ruling 1).

```ts
import type { SeverityRule } from "@/api/catalogue";
import type { SeverityLevel } from "@/ui";

/** S1 §5: at most 8 rules, a condition of at most 200 characters, a definition of at most 1000. */
export const MAX_RULES = 8;
export const MAX_WHEN = 200;
export const MAX_DEFINITION = 1000;

/** A rule being edited; `key` keeps React's row identity (and focus) through a reorder. */
export interface RuleDraft {
  key: string;
  when: string;
  severity: number;
}

let seq = 0;

export function newRuleKey(): string {
  seq += 1;
  return `r${seq}`;
}

/** A catalogue from before migration 0003 answers without the list: that reads as no rules. */
export function rulesOf(rules: readonly SeverityRule[] | null | undefined): RuleDraft[] {
  return (rules ?? []).map((r) => ({ key: newRuleKey(), when: r.when, severity: r.severity }));
}

export function toRules(drafts: readonly RuleDraft[]): SeverityRule[] {
  return drafts.map((d) => ({ when: d.when.trim(), severity: d.severity }));
}

/** Same order, same trimmed conditions, same levels. */
export function sameRules(a: readonly SeverityRule[], b: readonly SeverityRule[]): boolean {
  return (
    a.length === b.length &&
    a.every((r, i) => r.when.trim() === b[i].when.trim() && r.severity === b[i].severity)
  );
}

export function moveRule(drafts: readonly RuleDraft[], from: number, to: number): RuleDraft[] {
  const next = [...drafts];
  if (from === to || to < 0 || to >= drafts.length) return next;
  const [moved] = next.splice(from, 1);
  next.splice(to, 0, moved);
  return next;
}

export function onScale(level: number, scale: readonly SeverityLevel[]): boolean {
  return scale.some((s) => s.level === level);
}

/** The type's default severity when the scale has it; otherwise the lowest level. */
export function newRuleLevel(defaultSeverity: number | null, scale: readonly SeverityLevel[]): number {
  if (defaultSeverity !== null && onScale(defaultSeverity, scale)) return defaultSeverity;
  return scale[0]?.level ?? 1;
}

/** The first problem, named by rule number, or null. */
export function validateRules(drafts: readonly RuleDraft[], scale: readonly SeverityLevel[]): string | null {
  if (drafts.length > MAX_RULES) return `Keep to ${MAX_RULES} rules or fewer.`;
  for (const [i, d] of drafts.entries()) {
    const n = i + 1;
    const when = d.when.trim();
    if (!when) return `Rule ${n} needs a condition. Say when it applies, or remove it.`;
    if (when.length > MAX_WHEN) return `Keep rule ${n} to ${MAX_WHEN} characters or fewer.`;
    if (!onScale(d.severity, scale)) {
      return `Rule ${n} uses level ${d.severity}, which is no longer on the severity scale. Choose another level.`;
    }
  }
  return null;
}
```

```ts
export function toCreate(d: TypeDraft): CatalogueTypeCreate {
  const body: CatalogueTypeCreate = {
    name: d.name.trim(),
    colour: d.colour,
    kind: d.kind,
    group: d.group.trim() || null,
    default_severity: d.defaultSeverity,
    hotkey: d.hotkey || null,
  };
  const definition = d.definition.trim();
  if (definition) body.definition = definition;
  if (d.rules.length > 0) body.severity_rules = toRules(d.rules);
  return body;
}

/** Only what changed; the rules go as the whole ordered list when any of them changed or moved. */
export function toPatch(d: TypeDraft, t: CatalogueType): CatalogueTypePatch {
  const patch: CatalogueTypePatch = {};
  const name = d.name.trim();
  const group = d.group.trim() || null;
  const hotkey = d.hotkey || null;
  const definition = d.definition.trim() || null;
  const rules = toRules(d.rules);
  if (name !== t.name) patch.name = name;
  if (d.colour !== t.colour) patch.colour = d.colour;
  if (d.kind !== t.kind) patch.kind = d.kind;
  if (group !== (t.group ?? null)) patch.group = group;
  if (d.defaultSeverity !== (t.default_severity ?? null)) patch.default_severity = d.defaultSeverity;
  if (hotkey !== (t.hotkey ?? null)) patch.hotkey = hotkey;
  if (definition !== (t.definition?.trim() || null)) patch.definition = definition;
  if (!sameRules(rules, t.severity_rules ?? [])) patch.severity_rules = rules;
  return patch;
}
```
