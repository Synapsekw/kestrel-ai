## Budget

**C0 adds no background job and no new read.** Every new operation answers 501; the guards raise before any lookup; the passthroughs read a column of a row already loaded. The migration is the only runtime work: additive DDL plus one `UPDATE surface … WHERE kind = 'cloud_dsm'` (one row per cloud DSM, tens) and one unique index over `map_detection.finding_id` (all NULL; one pass over the table, no table rebuild). No `batch_alter_table`: plain `ALTER TABLE ADD COLUMN`, so `map_detection` (millions of rows possible) is never copied.

The contract **encodes** M's budget (spec §13) so the building units cannot drift from it:

- Background jobs: `importElevation` answers `202 SurfaceWithJob` (`elevation_import`); `createDrawingInspection` and `createDrawing` answer `202 …WithJob` (`drawing_import`, phases `inspect`/`build`). Nothing else M adds is a job.
- Bounded reads: a site tile is one 256 px PNG (`z` 0–20); a vector tile carries ≤ 20 000 vertices with `truncated`; findings in view ≤ 5 000 with `truncated`; profile ≤ 2 000 stations × ≤ 3 series (`stations_m` `maxItems: 2000`, `series` `maxItems: 3`); measurement vertices ≤ 5 000; georef ≤ 12 pairs; sample ≤ 8 surfaces; workspace state ≤ 64 KB (`state_too_large`); `listMeasurements` and `listMapMeasurements` are keyset pages (`limit` ≤ 1000, opaque `cursor`); surveys, layers and drawings are one row per item (tens).

## Global Constraints

- `contract/openapi.yaml` is the source of truth; `contract/client/schema.d.ts` is regenerated with `pnpm -C contract generate` and committed **in the same commit** as the YAML, never hand-edited. `pnpm -C contract check` runs `git diff --exit-code` on it, so stage it before running `check`.
- Names are exactly as this plan writes them (operationIds, paths **including path-parameter names**, schema names, parameter names, enum values, job types, event names). `test_every_spec_path_is_routed` compares path strings, and the B and W plans code against these names.
- Every new operation has `tags: [workspace]` (not `surfaces`/`volumes`: `tests/test_pointcloud_stubs.py` compares those tags with the S-routers' stubs), a `default: { $ref: "#/components/responses/Error" }` response, and a 501 stub until its unit lands.
- A request property never carries `default:`; the default goes in its `description` (ADR `2026-09-20-gotcha-openapi-default-makes-a-field-required-in-typescript`).
- In a YAML flow mapping (`{ ... }`) a `description` containing a comma or `": "` is double-quoted (ADR `2026-09-26-gotcha-yaml-flow-mapping-comma-splits-a-description`). A `summary` longer than one clause uses a `|` block.
- Every new component is referenced in the task that adds it (Spectral `oas3-unused-component: error`). Every example validates against its schema (Spectral `oas3-valid-schema-example`, `oas3-valid-media-example`). Every `*Page` example ends with `next_cursor: null` (Prism otherwise answers `"string"` and a paging client never stops).
- New fields on existing **response** schemas are `required` and filled by a one-line passthrough in the same task; new fields on existing **request** schemas are optional and guarded (501) until their unit.
- Migration `0012` is additive: new tables, nullable or server-defaulted columns, indexes; plain `ALTER TABLE` (no batch rebuild); the backfill never fails the upgrade. `down_revision` is `"0010"` while building and `"0011"` after Task 9 (R4).
- The shared backend interpreter is `$PY`; backend commands run from `<worktree>\backend`. No package is added.
- Frontend code passes `pnpm -C frontend lint` (ESLint, Prettier, `check-tokens.mjs`); run `pnpm -C frontend exec prettier --write <files>` on every TS file you touch.
- Stage by path, never `git add -A`, `git add .` or `git commit -a`. Every commit message ends with a blank line and `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Line numbers are `main`'s at `4ebcac1`; find each edit by the quoted text, which the plan always gives.

## Rulings (taken while planning; reviewers do not re-open them)

1. **Two kinds of transition, both 501.** New operations are 501 stubs (Foundation's pattern). New _request options_ on existing operations (`polygon_site`, `material`, `toe_lowest`, `region`, `category`) answer 501 `not_implemented` with `details {option, unit}` when used, from `app/workspace/pending.py`, and `OPTION_STUBS` in `test_contract.py` lets exactly those operations answer 501. Rejected: silently ignoring them (a region run would run over the whole map; a `material`-only PATCH would be refused as an empty patch with `validation_error`, which fails the contract test's positive cases), and implementing them here (M-B5's plan builds them). M-B5 deletes the guards, their call sites, the module and the `OPTION_STUBS` entries.
2. **`frame=site` is ignored until M-B1**, not 501: it is a read-only query key on five GETs, FastAPI already ignores unknown keys, the `*_site` response fields are optional and simply absent, and no W unit reads it before B1 is on `main`.
3. **`confirm_finding_delete` is ignored until M-B5**: before B5 no detection has a finding, so there is never anything to confirm.
4. **New response fields are passed through here**, not left to `BACKEND_PENDING`: `elevation_role`, `material`, `scope`, `region_px`, `category` each read their new column in one line, so every response conforms from this merge on (`test_volumes_api.py::test_results_validate_against_the_contract_schema` validates a real `VolumeMeasurement`), and the frontend gets non-optional types.
5. **`map_run.scope` and `site_area.category` are NOT NULL with server defaults** (`'map'`, `'general'`), not nullable as spec §12 lists them: B5's filters are `scope != 'region'`, and in SQL `NULL != 'region'` is not true, so a nullable scope would silently drop old runs from the timeline. Every existing row gets the default.
6. **`map_detection.finding_id` has no foreign key**, only a unique index `ux_map_detection_finding`: SQLite cannot add a foreign key without rebuilding the table, and `map_detection` can hold millions of rows. B5 keeps the link in its accept/reject/finding-delete paths.
7. **Four extra indexes for the measurements union** (M-B4 pages three providers by `created_at desc, id`): `ix_volume_measurement_created`, `ix_cloud_measurement_created`, `ix_map_measurement_created`, plus `ix_drawing_created` for B3's Data-list provider. C0 is the only migration writer (R4), so they go here.
8. **The union pages by `created_at`, not `updated_at`.** A keyset over a key that changes when a row is edited skips or repeats rows across pages. `MeasurementItem` carries both `created_at` (the page key) and `updated_at` (display).
9. **Union status and units are enums.** `MeasurementStatus` = `ready | computing | stale | failed` (a volume's `calculating` and C's cloud `computing` map to `computing`); `MeasurementUnit` = `m | m2 | m3 | deg | mm_per_m`; `headline` is a number (the client formats it). `MeasurementSubKind` = `point | distance | height | vertical | area | profile | volume` (C's `area` and `profile` cloud sub-kinds are valid values now).
10. **Drawings live in `backend/app/drawings/`** (the spec names no package). C0 creates the package with `startup.py`; M-B3 adds its router, jobs and paths there. B3 extends the sweep with partial-output cleanup under `drawings_dir`.
11. **Startup sweeps:** the drawing sweep is implemented fully here (it only needs the table); the `building` `dem` sweep **already exists** — `app/surfaces/startup.py::sweep_interrupted` fails every `building` surface of any kind — so C0 adds a test that pins it for `dem`. M-B2 may give `dem` its own wording ("import it again").
12. **No stub bodies for the new job types.** Nothing submits `elevation_import` or `drawing_import` before B2/B3 land (their routes are 501 stubs), so C0 only adds the names to the contract and the frontend label maps.
13. **The site-grid vectors are C0's**: B1 (`grid.py`) and W1 (`siteGrid.ts`) run in parallel and must test "on the same vectors" (spec §6), so the shared JSON fixture lands before either. `test_site_grid_vectors.py` checks it against a reference implementation of the §6 formulas.
14. **M's routers load only when the maps router did** (`api.py` block, the review router's pattern): `tests/test_api_maps_guard.py` asserts no path containing "map" survives a broken maps stack, and M's stack (rasterio, pyproj) breaks with it.
15. **The old volumes screen does not offer `toe_lowest`** (`PANEL_BASE_KINDS`): it would answer 501 until B5, and the new base cards are W4's.
16. **`/site-tiles/{kind}/{layerId}/{z}/{x}/{y}`** names its id parameter `layerId` (spec wrote `{id}`); `x` and `y` may be negative; `z` is 0–20. The raster knockout is a query key (`knockout`), not read from `layer_state`, because the tile is cached immutably by URL.
17. **A drawing's placement is one object** `{method: crs | embedded | none, crs?, units?}`, not a union, and an unplaced drawing has `georef: null` (spec §8.1's `method: null`). `transform` is always the affine form `E = a·x + b·y + c, N = d·x + e·y + f`, for both models.
18. **Map-measurement geometry is a vertex list** (`vertices: [[x, y], …]`, an area ring not closed), not GeoJSON, like `VolumeRing`. The DB column keeps the spec's name `geometry`.
19. **`setSiteFrame` takes `{kind: crs | local, epsg?}`** rather than the spec's `{epsg} | {kind: local}` union, so openapi-typescript emits a plain object type; a `crs` without `epsg` is 422 `invalid_epsg` (B1 adds the `REFUSES_VALID_DATA` entry).
20. **Controller reconciliation (2026-09-27), binding:** `SurfacePatch.captured_on`/`elevation_role` are M-B2 options guarded like M-B5's (`guard_surface_patch`, `OPTION_STUBS` unit `M-B2`); `nextUnreviewedMapDetection` takes `frame=site`; site tiles and vector tiles take `t` (preview affine, `no-store`, 422 `invalid_preview`) and `frame_key` (ignored by the server); `DrawingLabel.layer`; the sibling plans' error codes are declared on their operations (`outside_map`, `no_site_frame`, `not_in_site_frame`, `invalid_surfaces`, `surface_not_in_frame`, `measurement_limit`, `degenerate`, `invalid_preview`, `not_elevation`, `geographic_output`, `non_metric_output`, `invalid_patch`, and the S2 codes on `importElevation`); the `api.py` block lists one module per line so each unit inserts one line before `"app.workspace.stubs",`.

# New options on existing operations answer 501 until their unit builds them

## Context

The map-workspace contract unit (M-C0) lands every M operation before any M backend unit builds it,
as Foundation did. Foundation's mechanism covers new _operations_ (501 stubs, `EXPECTED_STUBS`) and
new _response fields_ (`BACKEND_PENDING`). M also adds _request options_ to operations that already
work: `polygon_site`, `material` and the `toe_lowest` base on volume create/patch, `region` on
`createRuns`, `category` on site areas. Schemathesis sends them in its positive cases. Ignored, a
region run would silently run over the whole map, and a `material`-only PATCH would be refused with
`validation_error` as an empty patch, which the contract test treats as a bug.

## Decision

- A request that uses a declared-but-unbuilt option answers 501 `not_implemented` with details
  `{option, unit}`, from one guard per option in `backend/app/workspace/pending.py`, before any lookup.
- `OPTION_STUBS` in `tests/test_contract.py` names the operations that may answer that 501; any other
  501 still fails the test.
- New response fields on existing schemas are required and passed through from their new column in
  the same change (never left to `BACKEND_PENDING`), so every response conforms from the merge on.
- Read-only query options (`frame=site`) are ignored until their unit: the fields they add are
  optional and simply absent.
- A new enum column that later code filters with `!=` is NOT NULL with a server default: in SQL
  `NULL != 'region'` is not true, so a nullable `map_run.scope` would drop every old run from the
